تسک هفتهٔ چهارم: سوپرمارکت امن، مرتب و آمادهٔ انتشار
سطح تحویل: قبولی، گام‌های ۰ تا ۵ برای بخش اصلی ۱۰۰ نمره‌ای. Bonus انجام نشده است؛ نمرهٔ نهایی با آموزشگاه است.

اجرا
همهٔ دستورها از داخل پوشهٔ دارای package.json اجرا می‌شوند؛ در این نسخه shops/yasaman/ است.
نسخهٔ تست‌شده: Node 22.14.0، TypeScript 7.0.2 و Vite 8.3.4.
قبل از npm ci سرورهای dev و preview را با Ctrl+C متوقف کنید تا فایل‌های نصب‌شده در ویندوز قفل نباشند.

npm ci
npm run check
node check-arch.mjs src --shop
npm run dev

برای نسخهٔ ساخته‌شده:
npm run build
npm run preview

build ابتدا TypeScript و معماری را بررسی می‌کند و فقط در صورت موفقیت هر دو، خروجی Vite ساخته می‌شود. Live Server و باز کردن مستقیم HTML روش اجرای این پروژه نیستند.
app.ts قدیمی حذف شده و ورودی جدید /src/main.ts است. هنگام انتقال نسخه روی هفتهٔ سوم، app.ts یا script.ts قبلی را نگه ندارید.
node_modules، dist و فایل‌های .env.*.local نباید وارد Git یا ZIP تحویل شوند. package-lock.json باید ثبت شود.

ابزار آکادمی
check-arch.mjs همان check.txt دریافتی است. در محیط آزمون، برابری بایت‌به‌بایت آن‌ها بررسی شد. ابزار برای بهتر شدن نتیجه یا حذف بررسی‌ها ویرایش نشده است.
خروجی کامل دستور node check-arch.mjs src --shop در arch-check.txt قرار دارد؛ ۲۰ فایل و تمام وابستگی‌ها پذیرفته شده‌اند.

پاسخ سؤال خطای TypeScript
پس از دریافت unknown، نمی‌توان مستقیم data.price را خواند. نمونهٔ واقعیِ اجرای کامپایلر در یک فایل آزمایشی، خطای TS18046 با متن 'data is of type unknown' داد. پس از افزودن Type Guard، همان آزمون با exit code صفر تمام شد. خروجی در type-check-example.txt است.
در برنامهٔ واقعی، getJSON داده را unknown برمی‌گرداند و loadList و isProduct قبل از ساخت کارت شکل آن را بررسی می‌کنند. وجود type به‌تنهایی دادهٔ سرور را در زمان اجرا معتبر نمی‌کند.

پاسخ سؤال تابعی که دو کار می‌کرد
کلیک افزودن در کد قبلی شمارنده را تغییر می‌داد و نمایش و پیام را هم انجام می‌داد. اکنون addToCart در src/cart/rules.ts فقط یک آرایهٔ جدید برمی‌گرداند؛ saveCart در src/storage/cart.ts فقط ذخیره می‌کند؛ render فقط نمایش را هماهنگ می‌کند. main این تابع‌های جدا را به رویداد متصل می‌کند. تابع ترکیبی addAndSave ساخته نشده است.

پاسخ سؤال معماری و npm run check
TypeScript صحت نوع‌ها و پیدا شدن ماژول را می‌سنجد؛ نمی‌داند ui نباید از api چیزی import کند. ممکن است چنین وابستگی‌ای از نظر نوع کاملاً درست باشد. ابزار check-arch.mjs مسیر لایه‌ها، دسترسی به document و fetch و localStorage، حلقه‌ها، نام فایل‌ها، توابع لازم و تعداد خط‌ها را بررسی می‌کند.

مالکیت داده و رفتار سبد
فقط شناسه و تعداد ذخیره می‌شوند؛ قیمت محلی ذخیره نمی‌شود و بعد از بازیابی دوباره از محصولات و تخفیف فعلی محاسبه می‌شود. اقلام ناشناس یا ناموجود حذف و تعداد بیش از موجودی اصلاح می‌شود.
جمع نمایشی تأیید سفارش نیست؛ کاربر می‌تواند مرورگر و localStorage را تغییر دهد. سرور هنگام سفارش واقعی باید موجودی، تخفیف و مبلغ را دوباره تأیید کند.
پکیج‌های notyf و canvas-confetti هفتهٔ سوم حفظ شده‌اند. پیام کتابخانه متن ثابت دارد و دادهٔ API وارد HTML آن نمی‌شود.

انتشار و API
.env.development: VITE_API_URL=/api
.env.production: VITE_API_URL=../../api
در dev و preview، proxy هفتهٔ سوم به API آنلاین آموزشگاه متصل است.
برای انتشار واقعی، محتویات dist را در /shops/<slug>/ قرار دهید و API باید در /api/ همان سرور باشد. هیچ راز یا کلید خصوصی در متغیرهای VITE_ قرار ندارد.
اگر آدرس نهایی صفحه یک سطح عمیق‌تر باشد، مانند /shops/info-hiding/info-hiding/، مقدار تولیدی قبل از build باید ../../../api باشد. برای مسیر مستقیم خواسته‌شدهٔ PDF همان ../../api درست است. محل پوشهٔ کد روی دیسک به‌تنهایی تعیین‌کننده نیست؛ مسیر نهایی انتشار مهم است.
dist نهایی با یک سرور فایل ساده، بدون Vite و بدون تغییر محتوای خروجی، زیر /shops/yasaman/ نیز تست شده است.

آزمون‌ها و تصاویر
browser-checks.json نتیجهٔ آزمون‌های dev، preview و سرور استاتیک را ثبت می‌کند.
در dev و preview، API آنلاین هنگام تست ۴۳ محصول، ۷ دسته و ۱۰ پیشنهاد داشت. سرور استاتیک با همان API محلی دست‌نخورده، ۱۶ محصول، ۵ دسته و ۴ پیشنهاد را درست نمایش داد.
تمام درخواست‌های اولیهٔ فایل‌ها و API در هر سه حالت ۲۰۰ بودند و در حالت عادی خطای Console یا استثنای مدیریت‌نشده وجود نداشت.
موجودی و تخفیف، جمع سبد، جلوگیری از افزودن بیش از موجودی، حذف، Refresh، سبد خراب، قیمت دست‌کاری‌شده در ذخیره‌سازی، جستجو، مرتب‌سازی، RTL/LTR و عرض‌های ۳۲۰، ۳۹۰، ۷۶۸ و ۱۴۴۰ بررسی شدند.
محصول نامعتبر، موجودی خراب، JSON خراب و 404 بررسی شدند؛ خطای درخواست شبکه در آزمون عمدی ممکن است در DevTools ثبت شود، ولی برنامه پیام مناسب می‌دهد و استثنای رهاشده ندارد.
متن شبیه HTML در نام محصول آزمایش شد و به‌صورت متن دیده شد؛ عنصر img یا کد اجرایی ساخته نشد.
Guardها و توابع خالص با آزمون‌های مستقلِ موجودی، قیمت، جمع و عدم تغییر آرایهٔ ورودی نیز بررسی شدند.
HTML با Nu Validator و html-validate و CSS با Nu Validator بدون خطا بررسی شدند.
