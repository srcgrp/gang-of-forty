# سوپرمارکت یاسمن — طراحی در یک صفحه

## ۱. نیازمندی‌ها

کاربر محصولات و تخفیف‌ها را می‌بیند، در فهرست کالاها جستجو می‌کند، دسته و ترتیب قیمت را انتخاب می‌کند و کالاهای موجود را به سبد اضافه یا از آن حذف می‌کند. تعداد و جمع سبد نمایش داده می‌شوند و سبد پس از بارگذاری دوباره باقی می‌ماند. یک محصول خراب نباید بقیهٔ فروشگاه را خراب کند.

پرداخت، ورود، ثبت سفارش واقعی، تغییر موجودی سرور و قیمت‌گذاری قطعی خارج از این نسخه‌اند. نگهداری جستجو در URL، ساختار Feature و تنظیمات سخت‌گیرانهٔ Bonus نیز خارج از محدوده‌اند.

## ۲. بخش‌های صفحه

سربرگ و جستجو، دسته‌های قبلی، پیشنهادهای ویژه، لبنیات، فهرست همهٔ محصولات با فیلتر و مرتب‌سازی، سبد خرید و پاورقی. ظاهر و دو پکیج هفتهٔ سوم حفظ می‌شوند. نام فروشگاه همچنان یاسمن است و از نمونهٔ API جایگزین نمی‌شود.

## ۳. داده‌ها و صاحب آن‌ها

| داده | صاحب و محل نگهداری |
|---|---|
| محصول، دسته، قیمت، تخفیف و موجودی | سرور؛ `Product`، `Category`، `Offer` و `Stock` |
| شناسه و تعداد اقلام سبد | State برنامه و `localStorage`؛ `CartLine` |
| حالت بارگذاری | State برنامه؛ `LoadState` |
| جستجو، دسته و ترتیب انتخابی | State برنامه؛ بعد از Refresh بازنشانی می‌شوند |
| آدرس پایهٔ API | فایل‌های عمومی `.env.development` و `.env.production` |
| بخش مقصد | Fragment مرورگر مانند `#dairy`؛ فیلترها به URL منتقل نمی‌شوند |

قیمت داخل سبد ذخیره نمی‌شود؛ ردیف‌ها و جمع از محصولات و تخفیف‌های معتبر فعلی محاسبه می‌شوند. سبد بازیابی‌شده با محصولات و موجودی فعلی تطبیق داده می‌شود.

## ۴. قرارداد API

هنگام شروع، `products.json`، `categories.json`، `offers.json` و `stock.json` هم‌زمان دریافت می‌شوند. آرایه‌های سه فایل اول و ساختار موجودی پیش از استفاده بررسی می‌شوند. محصول، دسته یا تخفیف نامعتبر کنار گذاشته می‌شود و تعدادش در Console با هشدار ثبت می‌شود. ساختار کلی اشتباه یا موجودی نامعتبر به حالت خطا می‌رود.

نوع `Shop` نیز مطابق `api/shop.json` محلی تعریف می‌شود؛ در این نسخه دریافت نمی‌شود، زیرا اطلاعات برند و تماس ثابت صفحه حفظ می‌شوند. همهٔ نوع‌ها در `src/types.ts` قرار دارند.

`getJSON` خروجی `Promise<unknown>` دارد. پاسخ HTTP ناموفق، JSON خراب و شکست شبکه خطا هستند. `broken.json` و `missing.json` فقط در آزمون‌ها جای درخواست اصلی را می‌گیرند؛ هیچ فایل API تغییر نمی‌کند.

## ۵. حالت‌ها

`loading`: پیام دریافت اطلاعات و مخفی بودن فهرست‌های خالی. `success`: نمایش محصولات معتبر و فعال شدن کنترل‌ها. `empty`: پیام نبود کالا بدون خطا. `error`: پیام فارسی قابل‌فهم و دکمهٔ تلاش دوباره.

جستجوی بدون نتیجه پیام مخصوص خودش دارد. سبد خالی پیام خالی بودن و جمع صفر نشان می‌دهد. نمایش حالت‌های اصلی با `switch` و بررسی `never` انجام می‌شود.

## ۶. پوشه‌ها و لایه‌ها

```text
src/types.ts       مدل‌ها؛ بدون import
src/api/           fetch، Type Guard و تبدیل unknown
src/storage/       فقط خواندن و نوشتن سبد در localStorage
src/catalog/       فیلتر، مرتب‌سازی، تخفیف و مدل کارت؛ توابع خالص
src/cart/          افزودن، حذف، تعداد و جمع؛ توابع خالص
src/ui/            فقط DOM و نمایش مدل‌های آماده
src/main.ts        State، اتصال رویدادها و شروع برنامه
```

جهت وابستگی‌ها از main به ui، logic و data و سپس types است. ui از قوانین یا API چیزی import نمی‌کند. منطق به DOM، شبکه یا ذخیره‌سازی وابسته نیست. هر فایل TypeScript حداکثر ۷۰ خط دارد. ابزار معماری آکادمی بدون تغییر استفاده می‌شود.

## ۷. امنیت و انتشار

کد مرورگر، متغیرهای `VITE_`، API عمومی و `localStorage` برای کاربر قابل مشاهده و تغییرند؛ هیچ کلید یا رمز محرمانه‌ای در آن‌ها نمی‌گذاریم. دادهٔ API و ذخیره‌سازی `unknown` است تا بررسی شود. متن محصول با `textContent` وارد DOM می‌شود و پیام کتابخانه ثابت است.

Type Guard فقط شکل داده را بررسی می‌کند و تضمین اصالت قیمت نیست. کاربر می‌تواند قیمت و جمع نمایشی را تغییر دهد؛ سرور هنگام سفارش واقعی باید قیمت، تخفیف، موجودی و مبلغ نهایی را دوباره محاسبه کند.

خروجی build در مسیر `/shops/<slug>/` و API در `/api/` قرار می‌گیرند. `base: './'` و آدرس نسبی تولیدی، خروجی را برای همین ساختار قابل انتقال می‌کنند. پیش‌نمایش و یک سرور فایل ساده هر دو آزموده می‌شوند.
