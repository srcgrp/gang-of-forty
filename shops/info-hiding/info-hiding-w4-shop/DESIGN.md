۱. نیازمندی‌ها و محدوده

کاربر محصولات و تخفیف‌ها را می‌بیند، در فهرست کالاها جستجو می‌کند، دسته و ترتیب قیمت را انتخاب می‌کند و کالاها را به سبد خرید اضافه یا از آن حذف می‌کند. تعداد اقلام و جمع سبد نمایش داده می‌شوند و سبد پس از بارگذاری دوباره باقی می‌ماند. نامعتبر بودن یک محصول نباید باعث از کار افتادن کل فروشگاه شود.

پرداخت، ورود، ثبت سفارش واقعی، تغییر موجودی سرور و تضمین قطعی قیمت در سمت کاربر خارج از محدودهٔ این نسخه‌اند. نگهداری جستجو در URL، معماری Feature و تنظیمات سخت‌گیرانهٔ Bonus نیز جزو محدودهٔ این تحویل نیستند.

۲. معماری و بررسی وابستگی‌ها

ساختار برنامه به لایه‌های types، api، storage، منطق cart و catalog، رابط کاربری ui و هماهنگ‌کنندهٔ اصلی main.ts تقسیم شده است.

فرمان بررسی معماری:

node check-arch.mjs src --shop

خروجی بررسی:

20 files, every import points down, no circles.

این ابزار جهت وابستگی بین لایه‌ها و نبود چرخهٔ import را بررسی می‌کند. ابزار بررسی معماری آکادمی بدون تغییر استفاده می‌شود.

۳. مدل داده‌ها و ایمنی TypeScript

تمام مدل‌های داده در src/types.ts تعریف شده‌اند؛ از جمله Product، Category، Offer، Stock، CartLine، LoadState و نوع‌های موردنیاز برای ورودی‌ها و خروجی‌های برنامه.

دادهٔ دریافتی از API ابتدا unknown در نظر گرفته می‌شود.

getJSON خروجی Promise<unknown> دارد.

پیش از استفاده از داده‌ها، Type Guardهای مربوط به محصول، دسته و تخفیف شکل داده را بررسی می‌کنند.

حداقل دو Utility Type و as const برای تعریف نوع‌ها و ثابت‌ها استفاده شده‌اند.

به‌جای enum از ساختارهای سازگار با الزامات تسک استفاده شده است.

تنظیمات tsconfig.json برای دور زدن بررسی نوع‌ها ضعیف نشده‌اند؛ از جمله noImplicitAny: false یا ignoreDeprecations به تنظیمات اضافه نشده‌اند.

خطاهای TypeScript با بررسی نوع‌ها رفع می‌شوند، نه با خاموش کردن بررسی کامپایلر یا استفاده از نوع‌های ناایمن.

Type Guard شکل داده را بررسی می‌کند، اما اصالت قیمت یا معتبر بودن تجاری آن را تضمین نمی‌کند.

۴. قرارداد API و مدیریت خطا

در شروع برنامه، فایل‌های products.json، categories.json، offers.json و stock.json هم‌زمان دریافت می‌شوند.

آرایه‌های محصولات، دسته‌ها و تخفیف‌ها و ساختار موجودی پیش از استفاده بررسی می‌شوند. موارد نامعتبر کنار گذاشته می‌شوند و تعداد آن‌ها با هشدار در Console گزارش می‌شود. خطای شبکه، پاسخ HTTP ناموفق، JSON خراب یا ساختار کلی نامعتبر به مسیر مدیریت خطا هدایت می‌شود.

broken.json و missing.json برای آزمودن خطاهای JSON خراب و فایل پیدا نشده استفاده می‌شوند و جایگزین درخواست‌های اصلی نیستند. فایل‌های API مشترک تغییر داده نمی‌شوند.

نوع Shop نیز مطابق ساختار api/shop.json تعریف شده است؛ اما اطلاعات برند و تماس در این نسخه ثابت می‌مانند و از آن فایل دریافت نمی‌شوند.

حالت‌های بارگذاری با LoadState به شکل یک Union Type تعریف می‌شوند:

loading: دریافت اطلاعات در حال انجام است.

success: محصولات معتبر نمایش داده می‌شوند.

empty: دادهٔ معتبر وجود ندارد.

error: خطا با پیام قابل‌فهم و امکان تلاش دوباره نمایش داده می‌شود.

حالت‌ها با switch مدیریت می‌شوند و بررسی never برای شناسایی حالت‌های فراموش‌شده به کار می‌رود. خطاهای broken.json و missing.json باید از مسیر خطای یکسان و پیام خطای قابل‌فهم عبور کنند.

۶. پیکربندی، بررسی‌ها و ساخت پروژه

ساختار فایل‌ها:

src/types.ts
src/api/
src/storage/
src/catalog/
src/cart/
src/ui/
src/main.ts

جهت وابستگی‌ها از لایه‌های بالاتر به لایه‌های پایین‌تر و در نهایت به types است. لایهٔ ui قوانین کسب‌وکار یا API را مستقیماً import نمی‌کند. types.ts نیز مستقل از سایر ماژول‌های برنامه است.

پیکربندی باید با ساختار Vite پروژه سازگار بماند و بررسی TypeScript را دور نزند. آدرس پایهٔ API از متغیر محیطی VITE_API_URL خوانده می‌شود:

.env.development: VITE_API_URL=/api

.env.production: VITE_API_URL=../../api

از base: './' برای مسیرهای نسبی خروجی build استفاده می‌شود. خروجی باید در ساختار پوشهٔ فروشگاه قابل انتقال باشد و مسیر API نیز با محل استقرار هماهنگ بماند.

بررسی‌های پذیرش:

node check-arch.mjs src --shop
npm run check
npm run build
npm run preview

بررسی معماری، جهت وابستگی‌ها را می‌سنجد؛ npm run check خطاهای TypeScript را بررسی می‌کند؛ npm run build امکان ساخت نسخهٔ تولید را می‌سنجد؛ و npm run preview برای بررسی نسخهٔ ساخته‌شده در مرورگر استفاده می‌شود.

۷. امنیت، شواهد و محدودیت‌ها

کد مرورگر، متغیرهای VITE_، API عمومی و localStorage برای کاربر قابل مشاهده و تغییر هستند؛ بنابراین هیچ کلید یا رمز محرمانه‌ای در آن‌ها قرار نمی‌گیرد. داده‌های ورودی پیش از استفاده بررسی می‌شوند و متن محصولات با textContent وارد DOM می‌شود.

کاربر می‌تواند قیمت یا جمع نمایشی را تغییر دهد. در یک سامانهٔ واقعی، سرور باید هنگام ثبت سفارش قیمت، تخفیف، موجودی و مبلغ نهایی را دوباره محاسبه و اعتبارسنجی کند.
